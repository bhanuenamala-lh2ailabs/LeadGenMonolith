# LeadGenMonolith: setup for a new machine

One repo that holds the consolidated lead-gen work: the SQLite database schema, the HubSpot sync, the daily funnel report, the Apollo credit ledger and the tools. It does NOT hold data. Business data, secrets and run outputs stay on each machine and are gitignored.

## What is in git, and what is not

| In git | Not in git (copy by hand, never commit) |
|---|---|
| Code (`leadgen/`, `tools/`, `tests/`) | `.env` (keys), `secrets/` (Google tokens) |
| Database schema as migrations (`db/migrations/`) | `db/leadgen.sqlite` (the data, ~3 GB) and `db/backup/` |
| Config (`config/`), rules (`CONTEXT.md`), docs (`docs/`) | `data/` (raw leads, PII), `out/`, `reports/` |
| `.env.example` (names only, no values) | Claude Code chat history (`chat_context/`, personal) |

## 1. Clone and install

```
git clone https://github.com/bhanuenamala-lh2ailabs/LeadGenMonolith.git
cd LeadGenMonolith
python3 -m venv .venv
.venv/bin/pip install -r requirements.txt
```

Python 3.9 or newer. The code avoids `X | Y` type hints, so 3.9 is the floor.

## 2. Secrets (never commit)

1. Copy `.env.example` to `.env` and fill every value from the secure channel (ask Bhanu). Keep the same variable names.
2. Copy the Google token files into `secrets/` (`companyops_sheets_token.json`, `hubspot_sheets_token.json`, `companyops_gmail_send_token.json`, and the client secret files). The `secrets/` folder is gitignored.
3. Check it works: `.venv/bin/python -m leadgen status`.

## 3. Pull everything from the three repos

LeadGenMonolith is built from three older repos. Put their folders next to this one, or give their paths on the command line. Each repo keeps its own `.env` and data; copy the data folders across as they are.

| Repo | Folder | What it provides |
|---|---|---|
| companyOps | `companyOps/` | Cluster 1 and 2 pipelines, TAM database `tam/data/tam.sqlite3`, Apollo audit ledgers, Claude Code chats |
| hubspot | `hubspot/` | CoOps Global and Coding funnel scripts, the IT Services TAM (`itsvc-tam/itsvc.db`), crm_mirror snapshots, Claude Code chats |
| RapidActionTeam | `RapidActionTeam/` | RAT funnel and mail scripts, RAT Claude Code chats |

Commands (from the repo root, after step 2):

```
.venv/bin/python -m leadgen migrate                                   # create the schema (all migrations, in order)
.venv/bin/python -m leadgen import-legacy tam --source ../companyOps/tam/data/tam.sqlite3
.venv/bin/python -m leadgen import-legacy repo-dbs                   # hubspot and RAT legacy databases
.venv/bin/python -m leadgen sync hubspot --account all                # live, read-only HubSpot pull
```

If your repos sit somewhere else, change the `--source` path. The legacy importers are read-only on the source databases.

**Claude Code chat context:** copy each repo's chat folder from `~/.claude/projects/<repo-path-with-dashes>/` into `chat_context/<repo>/`. These are personal and gitignored. Do not commit them.

## 4. Set up the database schema

`db/migrations/` is the schema, applied in order. `python -m leadgen migrate` runs them all, makes a backup first, and records each one with a checksum. To check the schema matches:

```
.venv/bin/python -m leadgen status
.venv/bin/python -m leadgen migrate        # re-running is safe: applied migrations are skipped
```

The latest migration is `0027_candidate_pool_reveal_detail.sql`. The data dictionary is `docs/DATA_DICTIONARY.md`, generated by `tools/gen_data_dictionary.py`.

## 5. Apollo credits: tracked dot to dot

Every Apollo call goes through `leadgen/apollo_ledger.py`. It writes one row per call (company or profile, purpose, segment, credits, what came back, where it went) before returning. Nothing else may call Apollo.

```
.venv/bin/python tools/apollo_tracker.py grant --credits N --note "top-up, approved by ..."   # record a top-up
.venv/bin/python tools/apollo_tracker.py meter                                                 # free balance reading
.venv/bin/python tools/apollo_tracker.py balance                                               # granted vs logged spend
.venv/bin/python tools/apollo_tracker.py report --by company|lead|purpose|caller
.venv/bin/python tools/apollo_tracker.py dot --from 2026-10-01 --to 2026-10-31 --csv out/apollo_dot.csv
.venv/bin/python tools/apollo_tracker.py unlogged                                              # meter spend minus logged spend (should be ~0)
.venv/bin/python tools/apollo_tracker.py scan                                                  # lists files calling Apollo outside the ledger
```

Rules: Apollo stays paused (`APOLLO_PAUSED=1` in `.env`). A run that spends credits needs the owner's go-ahead and `allow=True` in the call, and every call must give a purpose and a segment. Run `unlogged` before and after any Apollo job.

## 6. Daily funnel report

Dry run by default; `--send` mails it. Nothing schedules itself.

```
.venv/bin/python tools/daily_report_run.py                  # sync, owner snapshot, five-vertical report, no mail
.venv/bin/python tools/daily_report_run.py --send           # the same, and mail to the default recipient
```

Outputs go to `reports/vertical/<day>/` (`index.html`, `index.txt`, `snapshot.json`).

## 6a. The 5-vertical funnel: HubSpot stage automation, daily push, and the Performance Report

Five verticals run through HubSpot: Coding (3 portals — MAIN, CompanyOps, RAT, one pipeline each),
Company Ops Cluster 1, Company Ops Cluster 2, Company Ops Global, and RAT/Specialty Datasets. Each
funnel's stage flow (Cold Call → attempt chain → Interested → GMeet → close) lives as HubSpot deal
pipeline stages, not in this repo's code — `tools/hubspot_coding_properties_and_migration.py`,
`tools/hubspot_cluster1_properties_and_migration.py` and `tools/hubspot_cluster2_properties_and_migration.py`
are the one-time setup scripts that created those stages/properties; re-running one is a real pipeline
change, not idempotent housekeeping, so read the script before running it again.

**Queue → HubSpot push.** Each funnel has a Google Sheet "Queue" tab (sourced leads, `status: pending →
pushed/failed`) driving a bound Google Apps Script `dailyPush()` function — not this repo — that pushes
100 leads/rep/day in batched HubSpot API calls. The Apps Script projects are the source of truth for the
live push logic; this repo doesn't deploy them automatically. `tools/hubspot_delete_linkedin_sent.py` is
a one-off cleanup script, not part of the regular flow.

**`tools/daily_sync_pull.py`** computes WTD/MTD/ITD actuals vs targets for all 5 verticals from HubSpot
deal-stage history and writes two Google Sheets: the "Daily Sync" tab (Supply Team Mapping sheet) and the
Performance Report sheet's 5 per-vertical tabs (`--write-performance-report`). Dry-run by default; see the
file's own top-of-file comment for the full WTD/MTD/target-math logic, which is intentionally documented
in-line rather than here since it changes often. `tools/com.lh2.dailysync.plist` is an optional launchd
job that runs it every morning at 8am — install instructions are in the plist's own header comment; it has
hardcoded `/Users/bhanu/...` paths that need editing for any other machine before installing it.

**Sourcing playbook:** `docs/playbooks/icp_sourcing_playbook.md` — the ICP-qualify workflow a sourcing
script should follow (India-only, mobile-mandatory, SignalHire-before-Apollo-reveal, the per-vertical
headcount bands, and any standing exceptions like the hospital-headcount-200+ floor).

## Rules to read first

`CONTEXT.md` has the standing rules: HubSpot is read-only except through `tools/`, mail goes to the owner unless another recipient is named, no automated mailers or schedulers, +91 mobile and LinkedIn are hard gates for any push, and no learner, parent or tutor personal data is stored.
