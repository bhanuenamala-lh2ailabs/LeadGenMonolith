## 4. The 3 Oct itsvc org search, re-derived

**Rule** (measured 22:34-22:35 IST): 1 lead credit per `mixed_companies/search` call that returns at least one organisation, regardless of `per_page`; 0 for an empty result. Ten consecutive pages of one Pune partition returned 553 orgs and cost 6 credits (pages 1-6 returned orgs, 7-10 empty).

**What the run actually was.** `itsvc/pipeline.py --workers 10`: 2,940 partitions (28 cities x 7 headcount ranges x 15 keywords), `PER_PAGE=100`, up to 5 pages per partition, stop at the first page whose `total_pages` is reached. Final banner: 1,542 s, 139,720 org rows, 61,799 distinct, banner text "apollo spend : $0.00 (free endpoint only)". Preceded by two smoke tests and a first full run killed after ~2.3 min.

**Facts the first pass did not use.**

1. `/tmp/itsvc_run.log` contains **122 `[partition FAILED] ... HTTP 429 Too Many Requests`** lines (Jaipur, Indore and others). A failed partition is still counted as "done" and each made 5 rejected requests. Those requests were not billed (no organisations returned) but sit inside the request counter and cap the throughput near the key's `x-rate-limit-minute: 200`.
2. The `x-24-hour-usage` header is a per-endpoint request count, not credits: 4,217 at 14:26:15Z (`x-hourly-usage: 1`, a clock-hour bucket) then 4,231 at 17:05:50Z after exactly 14 more org-search calls (10 + 3 + the probe) with the 50-name xAI people/match run in between not moving it. So 4,217 = every org-search request since the start of 3 Oct UTC (smoke tests, run 1, run 2, probes), including the empty ones (free) and including or not 429-rejected ones (unknown).
3. Smoke tests: `--sample 2` yielded 1,000 rows = 2 partitions x 500 = 10 full pages; `--sample 3` yielded 1,104 rows = 500 + 404 + 200 = 12 pages. So 22 billed pages, not the 8 the first pass assumed.
4. Run 1 discovered ~7,178 candidate rows by 13:27:00Z (a `candidates` count taken in chat), i.e. ~16-20k org rows by the kill at 13:27:30Z at the 85 orgs/page seen in the first Pune partitions, i.e. ~230 pages (170 to 300), not 320.

**Run 2 estimate.** Let R2 = org-search requests of run 2 = 4,217 - run 1 (~345 requests) - 22 smoke - 3 probes ~ 3,830. Each hit partition costs `ceil(rows/100)` pages (<=5); each empty partition costs one free request; 122 died unbilled. Billed pages = requests - empty requests. From the database the partitions with at least one *new* org number 1,183 (`legacy_itsvc_raw_records`, distinct `task_key`), with rows per partition 572 under 10, 293 from 10-49, 98 from 50-99, 197 from 100-299, 23 from 300-499. Scaling those new-org counts so that the capped total equals the logged 139,720 rows gives ~2,150 pages for those 1,183 partitions, plus 100-600 pages for hit partitions whose orgs were all duplicates, i.e. **2,250 to 2,750**. The request-balance gives the same: billed = R2 - empties = 3,830 - (2,940 - 122 - H) = 1,010 + H, with H between 1,183 and ~1,800 hit partitions = 2,200 to 2,800. If the counter also counts the 610 rejected 429 attempts, billed drops to ~1,800-2,100. Adopted for run 2: **2,400 (2,000 to 2,900)**. The first pass took 2,860.

Total pre-22:34 org search: run 2 2,400 + run 1 230 + smoke 22 + three key/header probes + the 22:34 measured tests (9) = **2,664 (2,202 to 3,236)**, against the first pass 3,200 (2,400 to 4,200). The conclusion that nobody can know the exact figure without a baseline stands; the difference is that the likely value is ~2.7k, not ~3.2k. A dashboard check settles it: Apollo's usage by day for 3 Oct (UTC), action = organization search. Expected from this repo for that action: ~2.7k.

A rejected giant costs 1 billed call, a kept company with an India record 2, a company with no India record 0; the earlier size-check run (225 domains) showed 12 large / 19 small / 148 no-record, so ~11% of kept successes cost 2. Estimate **25 (12 to 45)**, not 90. The ad-hoc size probes, first pass 17, are **5** (Accenture and HHV tests 1 each, NR Consulting 1, only CAPRUS of the 14-name check had an India record: 2).

**COBOL batch 8 (killed on "stop every process").** First pass 320 (E). **UK batches: counter tail.** `build_leads.py` adds credits to its total only when a worker's result returns to the main loop and exits the loop as soon as the target trips the stop flag. With 6 workers, up to five mid-unlock/reveal tasks are uncounted: +0 to 60 on each of batch 1 (1,033) and batch 2 (990). Nearly every other script (Singapore, both UK batches, COBOL, CEO, fix rounds) sends `reveal_personal_emails: true` and counts 8 per reveal. The UI "Email" bucket was only 786 against ~4,433 reveals, so the extra is charged only when a personal email is found: expected hidden extra ~0.2 credit per reveal attempt, i.e. ~+150 across all counter-based runs (0 to +1,000 worst case). Not added to the rows except Singapore's ~40 and the high bounds.
